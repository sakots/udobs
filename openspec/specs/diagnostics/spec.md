# ログと通信診断

## Purpose

字幕転送の状態と通信障害を調査するための記録、その機密情報の扱いを定義する。診断で観測できなかった情報から障害原因を断定しない。

実装: [logging.ts](../../../src/logging.ts)、[error-details.ts](../../../src/error-details.ts)、[connection-diagnostics.ts](../../../src/connection-diagnostics.ts)、[index.ts](../../../src/index.ts)。確認用テスト: [logging.test.ts](../../../test/logging.test.ts)、[error-details.test.ts](../../../test/error-details.test.ts)、[udtalk-diagnostics.test.ts](../../../test/udtalk-diagnostics.test.ts)、[connection-diagnostics.test.ts](../../../test/connection-diagnostics.test.ts)。ログの読み方は[トラブルシューティング](../../../docs/troubleshooting.md)を参照する。

## Requirements

### Requirement: 起動ごとのログ保存

アプリは設定読み込みの前にログ保存を開始し、標準出力と標準エラーを画面に残したまま `logs/udobs-日時-プロセスID.log` へUTF-8で保存しなければならない（MUST）。保存行にはUTC日時と出力区分を付け、終了直前の記録をバッファに残さないよう同期書き込みを使わなければならない（MUST）。

ログ保存を開始できない場合は終了コード `1` で終了しなければならない（MUST）。開始後の書き込み失敗では一度だけ警告し、画面への出力を続けなければならない（MUST）。ログの自動削除は行わない。

#### Scenario: 複数行の字幕や警告を出力する

- **WHEN** アプリが複数行の標準出力と標準エラーを書き込む
- **THEN** 画面の出力を維持し、ファイルでは各行に日時と出力区分を付ける
- **AND** 終了処理を待たずファイルに内容が書き込まれる

### Requirement: 通信失敗と終了中断の区別

UDトークとの通信に失敗した場合は、初回から処理名、本文受信・解析を含む経過時間、通信全体と接続待ちの上限、エラーの名前・コード・メッセージ・内部原因を記録しなければならない（MUST）。終了操作による中断は通信失敗として記録してはならない（MUST NOT）。

#### Scenario: 本文の受信・解析で失敗する

- **WHEN** HTTP接続の成立後、応答本文の読み込みでエラーが起きる
- **THEN** 本文読み込みを含めた経過時間と失敗原因を記録する

#### Scenario: 利用者が取得中に停止する

- **WHEN** 終了操作で進行中の通信を中断する
- **THEN** その中断をUDトークの通信失敗として記録しない

### Requirement: 診断情報の範囲と秘匿

エラーの整形では既知の秘密値、HTTP URL、64桁の16進IDを伏せ、オブジェクト全体やスタックを出力してはならない（MUST NOT）。通信ヘッダーの診断は `Connection` の既知の値と `Keep-Alive` の `timeout`・`max` に限定し、未知の値を伏せなければならない（MUST）。Cookieやヘッダー全体を診断に保存してはならない（MUST NOT）。

この秘匿は通信診断の出力に対するものであり、アプリの通常ログに含まれる字幕本文や接続先をすべて匿名化する保証ではない。ログの共有には利用者による内容確認が必要。

#### Scenario: エラーにURLとセッショントークンが含まれる

- **WHEN** 通信エラーを診断用文字列へ整形する
- **THEN** URLと既知のセッショントークンを伏せ、エラーコードと内部原因を残す

#### Scenario: 未知のヘッダー値を受け取る

- **WHEN** `Connection` や `Keep-Alive` に許可していない値が含まれる
- **THEN** その値を非公開として扱い、ヘッダー全体を出力しない

### Requirement: 接続の観測と未観測の区別

接続診断は接続番号、IP、TCP・TLS成立通知と所要時間、接続再利用、TLSセッション再開、ALPN、要求・応答の接続関連ヘッダーを観測可能な範囲で記録しなければならない（MUST）。応答を受け取りヘッダーがない場合の `なし` と、応答自体を観測できない場合の `未観測` を区別しなければならない（MUST）。診断は対象通信を観測するだけで、通信方式や待ち時間を変更してはならない（MUST NOT）。

成功時の診断は、観測できた処理ごとの初回の新規接続・再利用と、失敗後の最初の成功で出力する。すべての成功通信を個別記録するものではない。

#### Scenario: TCP成立だけを観測する

- **WHEN** TCP成立通知を受けたが、TLS成立通知を確認できない
- **THEN** TCPを成立、TLSを未観測と記録する
- **AND** TLSの失敗が確認できたという意味にはしない

### Requirement: ソケット終了の記録と集約

通信完了後のソケット終了も記録しなければならない（MUST）。HTTP 200の応答が完了し、応答の `Connection=close` に従う正常な終了は、処理ごとに60秒間の件数へ集約し、それ以外は個別に記録しなければならない（MUST）。停止時には残った集計を出力し、監視を解除しなければならない（MUST）。

#### Scenario: ライブラリが正常な接続整理を通知する

- **GIVEN** HTTP 200の本文が完了し、応答の `Connection` が `close` である
- **WHEN** ライブラリの `UND_ERR_INFO` とメッセージ `reset` を伴ってソケットが閉じる
- **THEN** 正常終了の集計に含める
- **AND** `close.hadError=true` という情報だけで通信障害と判断しない

### Requirement: 字幕登録とOBS更新確認の区別

字幕の保持値を更新した時点と、OBSの成功応答を確認した時点をログで区別しなければならない（MUST）。保持値の更新は新規発話か訂正か、現在字幕・前字幕のどちらが変わったかを記録し、OBS更新確認には送信時の要求番号を含めなければならない（MUST）。

#### Scenario: OBSが切断中に字幕を受信する

- **WHEN** 字幕の保持値が更新されるが、OBSから成功応答を得ていない
- **THEN** 送信待ちへの登録を記録する
- **AND** その登録だけをOBS更新成功として記録しない

### Requirement: OBS再接続失敗の集約

OBSの最初の接続・認証失敗や切断は理由付きで警告し、その後の再接続失敗は1分ごとの件数と最後の理由へ集約しなければならない（MUST）。復旧時と停止時には残った件数を出力しなければならない（MUST）。この集約は `RECONNECT_MS` の再接続間隔を変更してはならない（MUST NOT）。

#### Scenario: OBSが停止したまま再接続を続ける

- **WHEN** OBSへの再接続が繰り返し失敗する
- **THEN** 初回の理由を警告し、以後の失敗を集約して記録する
- **AND** 設定した間隔での再接続は継続する
