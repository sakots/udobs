# obs-delivery

実装: [obs.ts](../../../src/obs.ts)  
テスト: [obs-client.test.ts](../../../test/obs-client.test.ts)、[delivery.test.ts](../../../test/delivery.test.ts)

## Purpose

既存のOBSテキストソースへ字幕を配送するWebSocket v5クライアントについて、認証、更新順序、応答確認、切断と復旧時の保持・再送を定義する。ログの詳細形式は本仕様の対象外とする。

## Requirements

### Requirement: OBS WebSocket v5の認証

クライアントは MUST Hello（op 0）に対して、`rpcVersion: 1`、`eventSubscriptions: 0`を含むIdentify（op 1）を送る。Helloがsaltとchallengeの両方を含む場合、`Base64(SHA256(Base64(SHA256(password + salt)) + challenge))`で求めたauthenticationを付ける。認証情報が不要なHelloではauthenticationを付けない。Identified（op 2）を受け取るまでは字幕更新を送信しない。

#### Scenario: 認証要求に応答する

- **WHEN** 現在の接続でsaltとchallengeを含むHelloを受け取る
- **THEN** 設定パスワードから算出したauthenticationを付けたIdentifyを送り、OBSイベントは購読しない

#### Scenario: 認証前に字幕を受け取る

- **WHEN** Identifiedを受け取る前に字幕更新が登録される
- **THEN** 本文を保持し、字幕更新要求は認証完了後に送信する

### Requirement: 既存テキストソースの設定更新

クライアントは MUST 指定された既存ソース名に対し、`SetInputSettings`の`inputSettings: { text }`と`overlay: true`で本文を更新する。ソースの作成やシーンへの追加は行わない。空のソース名に対する更新は無視する。送信対象が1ソースの場合は単発要求（op 6）とする。

#### Scenario: 単一の字幕ソースを更新する

- **WHEN** 認証済みで応答待ちのない状態で現在字幕を登録する
- **THEN** 設定されたソース名と字幕本文を持つ単発のSetInputSettings要求を送る

### Requirement: 字幕ペアをまとめて送る

字幕ペアの登録は MUST 現在字幕と前字幕の保持値・送信待ち値を両方更新してから送信を開始する。複数ソースを送る場合はSerialFrame（`executionType: 1`）、`haltOnFailure: false`のバッチ要求（op 8）を使用する。新しいクライアントで現在字幕ソースと前字幕ソースをペア登録した場合、要求は現在字幕、前字幕の順とする。送信順はソースごとの保持Mapへの初回登録順に従い、既存ソースの値の更新では順序を変更しない。バッチはOBS側での原子的な成功を保証するものではない。

#### Scenario: 現在字幕と前字幕を初めて送る

- **WHEN** 認証済みで他の更新がない状態から現在字幕Bと前字幕Aをペア登録する
- **THEN** BとAの両方を設定した後、現在字幕ソース、前字幕ソースの順のSerialFrameバッチを送る

### Requirement: 応答待ちを直列化して最新値へ集約する

クライアントは MUST 一度に1要求だけを応答待ちとし、その間に届く更新をソースごとの最新値へ集約する。対応する単発応答（op 7）またはバッチ応答（op 9）を受け取ってから次の送信待ち更新へ進む。

#### Scenario: 応答待ち中に字幕ペアが連続更新される

- **WHEN** 別要求の応答待ち中にペアC/B、続いてD/Cを登録する
- **THEN** 待機中に追加送信せず、対応する応答を受け取った後にD/Cを送る

### Requirement: 対応する全ソースの応答による成功確認

更新は MUST 要求IDが応答待ち要求と一致し、応答結果数が送信ソース数と一致し、全結果の`requestStatus.result`がtrueの場合にのみ成功確認済みとする。送信しただけでは成功確認済みとしない。件数不一致や失敗結果を含む対応応答でも当該要求の待機は解除し、次の送信待ち更新へ進む。応答失敗だけを理由とする同一値の自動再試行は行わない。

#### Scenario: バッチの一部だけが成功する

- **WHEN** 2ソースの要求に対し片方が失敗したバッチ応答を受け取る
- **THEN** ペア全体を成功確認済みとはせず、当該要求の待機を解除する

#### Scenario: 古い応答が遅れて届く

- **WHEN** 既に処理を終えた要求IDの応答が次の要求の応答待ち中に届く
- **THEN** 古い応答を無視し、次の要求の待機を解除しない

### Requirement: 未応答更新の5秒タイムアウト

クライアントは MUST 更新要求の送信後5000ms以内に対応応答を受け取れない場合、認証済み状態と応答待ちを解除して接続を閉じ、切断処理による再接続後に最新保持値を再送する。対応応答を処理した要求のタイマーは解除する。

#### Scenario: 更新の応答がない

- **WHEN** 送信した更新に対応する応答が5000ms届かない
- **THEN** 接続を閉じ、最新字幕を保持したまま再接続へ移る

### Requirement: 切断をまたぐ最新保持値の再送

クライアントは MUST 送信待ち値とは別にソースごとの最新保持値を維持する。切断時には応答待ち要求とそのタイマーを破棄するが、最新保持値は破棄しない。再接続でIdentifiedを受け取ったら、未応答だった送信中の値も含め、全ソースの最新保持値を送信待ちとして再構成して送る。切断中の複数更新は最新値だけを保持する。

#### Scenario: 未応答のまま切断し、その後更新する

- **WHEN** 「送信中」の更新応答前に切断し、切断中に現在字幕「最新」と前字幕「ひとつ前」を登録する
- **THEN** 再認証後には「送信中」ではなく「最新」と「ひとつ前」をバッチ送信する

#### Scenario: 切断中に更新がない

- **WHEN** 字幕ペアを送った後に切断し、本文を変更せず再認証が完了する
- **THEN** 直前の字幕ペアを再送する

### Requirement: 接続と認証の期限および再接続間隔

クライアントは MUST 接続開始からopenまで、およびopenからIdentifiedまでをそれぞれ5000msで打ち切る。接続開始の例外、接続・認証タイムアウト、現在の接続のclose後には、設定された`reconnectMs`を待って再接続する。現在の接続以外から届いたmessage、open、closeは状態変更に使用しない。

#### Scenario: 認証が完了しない

- **WHEN** 接続がopenした後5000ms経過してもIdentifiedが届かない
- **THEN** 接続を閉じ、`reconnectMs`後に新しい接続を開始する

#### Scenario: 古い接続から認証応答が届く

- **WHEN** タイムアウトした接続のIdentifiedが新しい接続の開始後に届く
- **THEN** 古い応答で認証済み状態にせず、新しい接続の認証完了を待つ

### Requirement: 停止後は再接続しない

`stop()`は MUST 停止状態にし、接続・認証・更新応答・再接続のタイマーを解除して現在のソケットを閉じる。停止後のソケットイベントは処理せず、`connect()`を再度呼んでも新しい接続を開始しない。

#### Scenario: 再接続待ち中に停止する

- **WHEN** 切断後の再接続待ち中にstopを呼び、再接続間隔を超えて時間が経過する
- **THEN** 新しい接続は開始されない
